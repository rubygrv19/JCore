# Ubuntu verification before release

Run Nuxt directly on the monitored Linux host as a dedicated unprivileged user. Running it inside a container without the host process namespace changes which processes it sees. Do not grant blanket sudo access to the web application.

1. Build on Ubuntu with the pinned pnpm lockfile (`pnpm install --frozen-lockfile`, `pnpm test`, `pnpm lint`, `pnpm typecheck`, `pnpm build`). Configure server credentials and the session secret through the service manager; Node production startup does not automatically load `.env`. Use HTTPS through the existing reverse proxy because production session cookies are Secure. Nuxt listens on loopback.
2. Validate collector configuration with `docker compose -f ops/vps/compose.yaml config --quiet`. Start it with `docker compose -f ops/vps/compose.yaml up -d`. Verify listeners using `ss -ltn`; ports 9090 and 9100 must bind only to 127.0.0.1. Keep the existing proxy configuration intact.
3. Inspect `http://127.0.0.1:9090/api/v1/targets`. The node-exporter target must be UP. Check recording and alert rules with `docker compose -f ops/vps/compose.yaml exec prometheus promtool check rules /etc/prometheus/vps.rules.yml`. Allow time for rate queries and history to accumulate.
4. As the application user, verify read access to `/proc/stat`, `/proc/meminfo`, process status files, `systemctl list-units --all --type=service`, `systemctl show <actual-unit>`, and `ss -ltnup`. D-Bus, hidepid, and socket ownership restrictions can make fields unavailable; the API must return null/partial rather than invented data. Ports are only those visibly owned by MainPID. No socket ownership is not proof of no listeners.
5. Select expected states from real deployment units. Recommended candidates are the actual JCore service, its reverse proxy, and docker.service if Docker hosts the collectors. Verify names first. Set `NUXT_VPS_EXPECTED_SERVICES` to a JSON object such as `{"your-app.service":"active"}`. Leave other units unknown. Do not assume every enabled or installed unit must be active.
6. Sign in and compare `/api/vps/dashboard` with Prometheus queries and OS readings. CPU and I/O rates use five-minute windows; do not expect equality with instantaneous top readings. Compare memory with MemAvailable, filesystem capacity with available-to-unprivileged space, and service state/PID with systemctl. Compare process start time with `ps -p <pid> -o lstart=`. Process CPU needs two samples and represents total host capacity.
7. Confirm dashboard/source timestamps, nullable fields, schema 1.4, and explicit pending/firing labels. A process permission failure must not expose credentials. Command arguments are intentionally hidden.
8. On a controlled staging host, stop only the collector service and verify unavailable/stale feedback, then restore it and verify recovery. Do not stop production application services merely to test monitoring. Test alert timing using promtool test rules or controlled staging load.
9. Exercise pagination through two refresh cycles, navigate away/back, and verify no polling remains after leaving. Test mobile/desktop and light/dark themes. Check 401 for private APIs without a session and 429 after the login attempt budget is exhausted.

The per-process login limiter allows 10 attempts per minute across all callers and resets on restart. If deployment uses multiple workers or instances, enforce a shared limit at the trusted proxy as well. No public access is allowed to Prometheus or Node Exporter.

Record actual command outputs and platform details when running this checklist. Passing macOS tests and mocked integration tests does not prove Ubuntu collector permissions or host metric availability.
